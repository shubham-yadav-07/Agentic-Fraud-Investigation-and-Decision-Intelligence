# ARGUS: Agentic Fraud Investigation and Decision Intelligence

*From uncertain signals to defensible action.*

ARGUS is a full-stack **agentic fraud investigation and decision intelligence platform** built to transform uncertain fraud signals into structured, evidence-driven investigations. It combines a **FastAPI backend, SQLite database, graph and policy analysis, role-based authentication, and an interactive web interface** to provide a complete case investigation workflow.

The platform analyzes relationships between entities, evaluates relevant policies, processes investigation data, and generates structured findings while keeping investigators informed of each stage of the investigation. Instead of simply flagging suspicious activity, ARGUS focuses on understanding **what happened, why it matters, what evidence supports it, and what action can be considered**.

## What is real and what is not

| Real, and tested | Not real yet |
|---|---|
| REST API with sign-in, roles and an audit trail | The data is **synthetic**, generated by `backend/seed.py` |
| SQLite database that keeps cases, evidence, decisions and memory between restarts | No TigerGraph, MCP or GraphRAG service. SQLite tables stand in for the graph (see `docs/INTEGRATION.md`) |
| Agent workflow that computes risk, confidence, uncertainty and evidence sufficiency from the data | The agent is a deterministic rule engine, not a language model |
| Graph traversal, similar-case retrieval and policy retrieval (text similarity plus a graph link) | Policy text is sample text written for the demo |
| Evidence requests, including a public customer link that works without signing in | The customer link is not connected to SMS, email or a bank app |
| Server-side approval rules: only an approver or admin can approve or reject | The 20 "official" benchmark cases are synthetic placeholders |
| 9 automated backend tests | No HTTPS, rate limiting or production hardening |

## Quick start

Needs Python 3.10 or newer.

```bash
./run.sh            # creates .venv, installs dependencies, starts the server
# open http://localhost:8000
```

Or by hand:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --port 8000
```

The database is created and filled on first start (about one second). Interactive API docs are at `http://localhost:8000/docs`.

With Docker (not tested in the environment this was built in):

```bash
docker build -t argus . && docker run -p 8000:8000 -v argus-data:/app/data argus
```

## How the agent decides

All numbers come from `backend/scoring.py` and `backend/engine.py`.

| Quantity | Rule |
|---|---|
| **Risk** (0 to 99) | 5 base, plus 30 x min(amount / account average / 10, 1), plus 22.5 x min(other accounts on the device, 3) / 3, plus 20 x best similarity to a confirmed-fraud case, plus 8 for a first-time merchant and 3 for a risky merchant category |
| **Evidence sufficiency** | Sum of what has been found: transaction signal up to 22, history 10, graph links 20, similar case 20 x similarity, policy 8. Customer validation adds 18, step-up 16, analyst request 12 (capped at 98) |
| **Confidence** | 0.86 x sufficiency, plus 10 when a direct customer or step-up answer agrees with the risk direction |
| **Uncertainty** | 100 minus confidence |
| **Gap** | Sufficiency below 85. The agent asks for evidence. If all three evidence types are used and it is still short, the case goes to an analyst |
| **Evidence result** | Adverse: risk rises by 14, 12 or 10. Confirmed: risk falls to 45% of its value (minimum 18) |
| **Recommendation** | Risk 75 or more: escalate (needs approval). 55 to 74: monitor account. Below 55: allow with monitoring |
| **Low-risk shortcut** | Risk below 35 skips customer validation (policy 5.1) |

Similar cases are ranked by: earlier case on an account sharing the device (0.40) or IP (0.20), same fraud pattern (0.25), same merchant category (0.10) and closeness of amount (0.15).

Policy retrieval scores each section by TF-IDF text similarity to a description of the case, plus 0.25 when the section is linked to the case's fraud pattern through a typology. This is a small stand-in for GraphRAG.

## Architecture

![Architecture](docs/architecture.png)

```
backend/
  main.py        API routes, auth, case detail assembly, static file serving
  engine.py      investigation workflow, evidence requests, approvals, closing
  scoring.py     risk, similarity and sufficiency scoring
  graph.py       every graph query (the seam for TigerGraph)
  retrieval.py   policy retrieval
  policies.py    sample policy sections and typologies
  db.py          schema and write helpers
  security.py    password hashing and signed session tokens (standard library only)
  seed.py        synthetic dataset and demo cases
  config.py      environment settings
frontend/
  index.html, assets/app.js, assets/app.css    the interface (plain JavaScript, no build step)
  customer.html                                the public page a customer opens to answer a request
tests/           API tests (pytest)
docs/            integration guide, API notes, screenshots, diagrams, project record
```

The investigation runs on a background thread and saves every step. The interface polls the case every second, so it shows what the backend has actually done. A page refresh or a second browser shows the same state.

## API summary

| Method and path | Purpose |
|---|---|
| `POST /api/auth/login`, `GET /api/auth/me` | Sign in, current user |
| `GET /api/cases`, `GET /api/stats` | Open cases and headline numbers |
| `GET /api/cases/{id}` | Full case: timeline, evidence, findings, graph, prior cases, meters |
| `POST /api/cases/{id}/investigate` | Start the investigation |
| `POST /api/cases/{id}/evidence-requests` | Ask for customer validation, step-up authentication or an analyst request |
| `POST /api/evidence-requests/{id}/respond` | Answer a request (signed-in user or customer link token) |
| `POST /api/cases/{id}/approval` | `approve`, `reject` or `more_evidence` (approver or admin) |
| `POST /api/cases/{id}/apply` | Apply an action that needs no approval |
| `POST /api/cases/{id}/history` | Pull a case from memory into the graph |
| `GET /api/memory`, `/api/cases/{id}/policy`, `/api/cases/{id}/report`, `/api/benchmark` | Memory search, policy retrieval, case record with audit trail, benchmark status |
| `POST /api/admin/reset` | Rebuild the demo data (admin) |

## Configuration

Environment variables (see `.env.example`): `ARGUS_SECRET`, `ARGUS_DB`, `ARGUS_STEP_DELAY`, `ARGUS_THRESHOLD`, `ARGUS_TOKEN_HOURS`.

## Tests

```bash
pytest
```

The tests start the app on a temporary database and cover sign-in, the headline numbers (82, 67, 33 and 78, then 96 after a denial), the evidence loop, the public customer link, role enforcement, the low-risk policy shortcut, reject and more-evidence paths, memory, policy retrieval and reset.

## Deploying

Any host that runs a long-lived Python process works, for example Render, Railway or Fly.io. Start command: `uvicorn backend.main:app --host 0.0.0.0 --port $PORT`. Attach a persistent disk for `ARGUS_DB`, and set `ARGUS_SECRET`. Serverless hosts that run functions per request (including Vercel) do not suit this app, because the investigation runs on a background thread and SQLite needs a disk.

## Connecting the real stack

See [`docs/INTEGRATION.md`](docs/INTEGRATION.md) for how to replace the seed data, the graph functions, the retrieval and the rule engine with TigerGraph, GraphRAG and an LLM orchestrator without changing the interface.

## Known limitations

Synthetic data, sample policy text, a rule engine instead of a model, SQLite (one writer at a time), no HTTPS or rate limiting, demo passwords, and an interface that polls instead of using a push connection. `docs/ARGUS_Project_Record_prototype.docx` describes the original front-end-only prototype and the full product design.
